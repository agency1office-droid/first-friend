# 운영 기능 확장 — 2026-09-07

현재 플랫폼의 페이지·API·초기 스키마·인증·외부 연동 코드를 확인하고, 기존 입양 심사 콘솔을 전체 플랫폼 운영 콘솔로 확장했다. Tabler Fluid Vertical 정보 구조를 유지하며 SEED SideNavigation, Dialog, Select, TextField, Checkbox, ActionButton, Callout을 사용했다. TDS나 새 실행 UI 의존성은 추가하지 않았다.

## 구현 범위

| 영역 | 사용할 수 있는 기능 |
|---|---|
| 운영 요약 | 업무별 전체/대기 건수, 조회 실패 구분, 공공 동물 동기화 상태, 소셜 로그인 환경 설정 존재 여부, 이메일 설정 상태 |
| 회원 | 이름·이메일·번호 검색, 연결된 소셜 로그인/이메일 인증 확인, 마케팅 동의 조회, 이름·지역 수정, 제재/해제, 모든 세션 종료 |
| 콘텐츠 | 이야기·질문·답변·그림·보호소 소식 검색, 공개 여부 필터, 상세 내용 수정, 숨김/복구. 공개 조회에서도 숨김 반영 |
| 보호소 | 등록 보호소 조회와 이름·지역·소개 수정. 전문 역할 부여는 기존 증빙 심사를 사용 |
| 입양 | 기존 신청·직접 등록·역할 인증·외부 입양 인증·인계·돌봄 위기 처리 유지 |
| 안전 | 신고 접수/해결/종료, 게시글 및 계정 조치, 이의제기 검토, 실종 신고 상태 처리 |
| 봉사 | 공고 열기/닫기, 지원 승인/미승인/완료. 모집 인원 확인, 완료 시 첫 봉사 배지, 상태 알림 |
| 후원 | 후원·제휴 의향 연락/종료, 모금 참여 의향 조회. 의향 금액을 실제 결제액으로 표시하지 않음 |
| 고객 문의 | 회원 문의 접수, 본인 문의와 답변 조회, 관리자 답변/종료/재접수, 답변 앱 알림 |
| 마케팅 | 이메일/앱 알림 캠페인 초안 작성·수정, 역할별 대상 선택, 내부 URL 연결, 수신 동의자 큐 생성, 10건씩 발송, 미처리 건 취소 |
| 발송 기록 | 대기·처리 중·접수·실패·제외 조회. 이메일 제공자 접수 번호와 오류 구분 |
| 동의 | 기본 미동의, 이메일/앱 마케팅 개별 동의·철회, 변경 이력, 이메일 수신 거부 링크 |
| 추적 | 새 데이터 변경과 감사 기록의 단일 DB 트랜잭션, 오래된 화면의 덮어쓰기 차단, 중복 요청 차단 |

회원의 비밀번호·토큰·소셜 제공자 사용자 식별값은 운영 응답에 포함하지 않는다. 관리자 자신/다른 관리자에 대한 제재·프로필 변경은 이 화면에서 막는다. 일반 회원과 보호소 계정은 관리자 전용 API에 접근할 수 없다.

## 아직 완료할 수 없는 항목과 다음 조치

| 항목 | 이유 / 필요한 이유 | 진행 방법 |
|---|---|---|
| 실제 이메일 전송 및 수신 확인 | RESEND_API_KEY, EMAIL_FROM, EMAIL_REPLY_TO가 없다. 외부 메일 전달을 위해 필요 | Resend에서 firstfriend.me 발신 도메인 DNS 인증 → Vercel Production에 위 서버 변수 등록 → 본인 수신 동의 계정으로 발송 점검. 현재는 설정 없으면 발송 준비를 차단하고 초안을 보존 |
| 외부 수신 메일함·반송/스팸 자동 수신 | 메일 수신 도메인/웹훅이 연결되지 않음 | 수신 라우팅과 서명 검증 웹훅을 구성한 뒤 발송 기록에 delivered/bounced 상태 연결. 현재 accepted는 제공자 접수이며 도착 보장이 아님 |
| 예약·무인 대량 캠페인 | 현재 운영자가 10건 단위로 직접 처리 | 발송량 증가 시 스케줄러·큐 워커 추가. 실패/처리 중 메일은 중복 방지를 위해 자동 재발송하지 않고 제공자 로그 확인 |
| 문자·푸시·공식 보호센터 전송·결제/환불·배차 | lib/integrations.ts의 기존 외부 어댑터는 더미이며 계약/키가 없음 | 사업자 계약과 실제 API 연결 후 정산·전달 결과 검증. 앱 알림과 의향 기록은 실제 DB 저장 |
| 외부 광고 성과·전환율·유입 분석 | 이벤트 수집/광고 계정 연동이 없음 | 수집 목적과 동의를 정하고 이벤트 계측·광고 계정 연결. 현재 회원/신청 등 실제 DB 건수만 표시 |
| 계정 영구 삭제·임의 관리자 권한 부여 | 입양 동의/분쟁/인계 기록과 FK가 얽혀 있어 일괄 삭제로 처리하면 안 됨 | 고객 문의에서 요청 접수 후 본인 확인·보존 대상 구분·익명화 절차 구현. 전문 역할 인증은 기존 심사 기능 사용 |
| DB 백업 복구 훈련 | 코드만으로 호스팅 계정 백업 정책/복구 가능성을 보증할 수 없음 | Supabase 백업 보존·요금제 확인과 별도 복원 검증 필요 |

발송 구현은 [Resend 공식 Send Email API](https://resend.com/docs/api-reference/emails/send-email) 규약을 따른다. API 접수 후 불확실한 결과는 자동 재시도하지 않는다. 수신 대상은 큐 생성과 발송 직전에 각각 동의·제재·주소 인증을 확인한다. 취소 시 이미 외부 제공자에게 제출된 메일은 회수할 수 없다.

## 검증 방법

- `npm run lint`
- `npm test`: 기존 테스트에 관리 API 접근 통제·버전 검증·메일 미설정 차단·민감 필드 제외 검증 추가.
- `tests/operations-management.sql`: 격리된 PostgreSQL 호환 DB에서 실행 후 rollback. 제재·세션 종료·관리자 보호·동시 수정·감사 실패 rollback·동의 대상·동의 철회·이메일 인증·앱 알림 중복 방지·문의 답변을 검증한다.
- 로컬 Chrome에서 실제 빌드와 격리된 테스트 데이터를 사용해 데스크톱/모바일 레이아웃·회원 수정·확인 단계·뒤로가기를 검증한다. 이 결과는 운영 계정 실사용 검증과 구분한다.
- 마이그레이션은 기존 GitHub Actions `Supabase migrations`를 통해 적용한다. Vercel은 origin/main push의 Production 자동 배포를 사용한다.
